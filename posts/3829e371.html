注意这里有个容易被忽略的点：MapReduce 的输出是纯文本（part-00000），不是数据库表，也不是 Excel。它能直接被 Pandas、Excel、BI 工具读取，因为它就是 \t 分隔的 TSV。这既是 Hadoop 的简单之处，也是它的局限——不做索引、不做事务。

二、环境准备

Ubuntu Server 22.04 自带 python3.10，但没装 Pandas 和 Matplotlib：


验证：

预期 pandas 1.3.5 | matplotlib 3.5.1。

为什么用 apt 而不是 pip3 install？

  1. Ubuntu 的 python3-pandas 是预编译好的二进制包，装完即用；pip 在某些环境会尝试从源码编译，编译失败率很高（缺 gcc、libpython3-dev）。
  2. 系统包由 apt 统一管理，不会和系统自带的 numpy 版本打架（Pandas 对 numpy 版本有硬要求）。
  3. 不用建虚拟环境——这台机器只跑自己的脚本，不需要隔离。
    如果你习惯用 pip，记得加 --break-system-packages 或者用 venv，否则 Ubuntu 22.04 之后会直接拒绝安装。

三个细节：

设置 作用 不设置会怎样
matplotlib.use("Agg") 用文件渲染后端 报 no display name and no $DISPLAY environment variable

Noto Sans CJK JP 排第一个不是笔误。 fonts-noto-cjk 装的是 NotoSansCJK-Regular.ttc（一个字体集，含 JP/KR/SC/TC 多种），Matplotlib 只认 JP 这个名字，写 Noto Sans CJK SC 反而可能找不到。列表里三个名字是从「一定能命中」到「兜底」的顺序。

indicator=True 是保险：如果某个店铺只在 HDFS 结果里出现（比如 reducer 写了但 mapper 漏读），_merge 会是 left_only，立刻暴露。

踩坑记录：KeyError: 'sales_hdfs'
最初我写的是 hdfs.merge(local, on="shop", suffixes=("_hdfs", "_local"))，然后取 m["sales_hdfs"]——直接报 KeyError。
原因：suffixes 只对「两边同名的列」生效。这里 HDFS 侧是 sales/gmv，单机侧是 total_sales/total_gmv，名字本来就不冲突，Pandas 不会加后缀。
修法有两种：给 HDFS 侧的列先重命名（上面脚本的做法），或者 merge 后按真实列名取。遇到 KeyError 先 print(m.columns)，比猜快十倍。

6.3 图二：销售额占比

6.4 图三：商品价格分布


这两张图看起来“没信息量”，但恰恰说明了数据的性质。

  • 价格直方图几乎是一条平线（每个价格区间都是 2200 — 2500 件）
  • 饼图里 10 个店铺每家都是 10% 左右
    原因很简单：这份数据是 random.uniform(19, 2999) 和 random.choice(20 家店) 生成的——均匀分布。均匀分布画出来就是平的、就是均等的，这是数学必然，不是分析失败。
    真实电商数据完全不同：价格是右偏长尾（大量低价商品 + 少量高客单价），销量是幂律（头部店铺吃走大部分流量）。换真实数据后，饼图会变成“前三家占 60%”的样子，直方图会堆在左侧。
    所以写报告时一定要标注数据来源：这份数据用于验证链路，不用于业务结论。

七、Hadoop 与 Pandas 的实测对比

同一份 9.35 万条数据，同样的聚合逻辑，两种实现：

维度 单机 Pandas Hadoop Streaming
处理框架 单进程、内存计算 YARN 调度 + 3 节点并行
提交到出结果 PANDAS HADOOP
代码量 8 行 mapper 16 行 + reducer 22 行
启动开销 无 JVM 启动、Container 分配、任务分发、Shuffle 落盘
数据规模上限 受单机内存限制 受集群磁盘总量限制
结果一致性 基准 与单机完全一致 ✓

倍率：约 RATIO 倍。 小数据量下 Hadoop 慢这么多，是正常且必然的。

为什么慢

环节 单机 Pandas Hadoop
启动 解释器加载 ~0.2 秒 JVM + YARN 调度 + 3 个 Container 分配
数据读取 本地 read_csv 顺序读 HDFS 分块读 + 网络传输到各节点
计算 内存里 groupby Map 序列化 → Shuffle 落盘 → Reduce 反序列化
结果 直接返回 写 HDFS（3 副本）再读出

关键在固定开销被摊薄：Hadoop 那 1 分多钟里，绝大部分是 JVM 启动、资源申请、任务调度，真正算数据的时间可能只有几秒。数据量到 500 GB 时，这部分开销几乎不变，而计算时间会线性增长——交叉点出现了，Hadoop 才开始赢。

什么时候该用 Hadoop

场景 建议 原因
< 10 GB ❌ 别用 单机 Pandas / DuckDB 快几十倍
10 GB — 1 TB ✅ 可以考虑 并行收益开始超过调度开销
> 1 TB 或需要长期存放 ✅ 必须 单机磁盘装不下，HDFS 能横向扩
数据已在 HDFS 上 ✅ 就地算 避免”先拉到本地再算”的网络传输

我专门做了对比：同一份 9.3 万条数据，Hadoop Streaming 要 1 分多钟，单机 Pandas 只要零点几秒。Hadoop 慢在 JVM 启动、YARN 调度、Shuffle 落盘这些固定成本上，数据量小完全划不来。

但把数据量放大到 500 GB、分成 4000 个块并行，这个固定开销就被摊薄了，那才是 HDFS + MapReduce 的战场。我做这个对比是为了搞清楚边界在哪——什么时候该用它、什么时候老老实实用 Pandas。

另外我用 Pandas 做了结果对账：20 个店铺的销量和金额，分布式与单机计算完全一致。

8.3 Xshell 的 sz（需要装 lrzsz）

Xshell 会弹保存对话框。一次一个文件，麻烦，但不用配网络。

九、常见报错

报错 原因 解法
图里中文全是方框 □□□ 没装中文字体 sudo apt install -y fonts-noto-cjk + fc-cache -fv
no display name and no $DISPLAY 用了默认后端 脚本开头加 matplotlib.use("Agg")
KeyError: 'sales_hdfs' merge 的 suffixes 没生效 先给列重命名，见第五节的坑
ModuleNotFoundError: pandas 装的是 pip 环境，跑的是系统 python 用 sudo apt install python3-pandas
负号显示成方框 没设 axes.unicode_minus plt.rcParams["axes.unicode_minus"] = False
scp 报 Permission denied (publickey) 没配密钥且密码输错 重新输密码，或先 ssh-copy-id
饼图标签重叠 类别太多 只取 TOP 10 + 其余合并成“其他”
